Coming from C, I’m used to thinking about memory in terms of manually managing malloc and free, so learning how Rust handles ownership was a big mental shift. At first, it felt strange that simply assigning let s2 = s1; would make s1 unusable, but connecting it back to stack pointers and heap allocations made everything click. Without invalidating the original variable, both variables would try to free the same heap memory at the end of the scope, causing a double fre in c, which is why it's just automatically invalidated in rust. Comparing fixed-size types like i32 (which implement Copy) with heap-allocated types like String (which move by default unless explicitly cloned) showed how Rust forces memory costs to be visible. Testing the compiler errors myself and verifying where the AI slightly overstated things—like realizing Rust prevents double-frees and use-after-frees at compile time rather than guaranteeing zero memory leaks altogether—gave me a much clearer picture of how the borrow checker actually protects memory before a program even runs.
